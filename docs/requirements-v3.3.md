# 領収書作成Webアプリ 要件定義 Ver.3.3

出典：ChatGPTとの対話で確定した要件定義Ver.3.3（Orca引き継ぎプロンプトの §1〜§7 を転記）。
本書は引き継ぎ時点の記録であり、変更は人間の承認を要する。

---

# 1. プロジェクト概要

- プロジェクト名：領収書作成Webアプリ（リポジトリ名 `receipt-app`）
- 目的：誰でも無料で簡単に領収書を作成・PDF保存・印刷できるWebサービス。将来的には発行者・宛先のマスター管理、一括発行、発行履歴、訂正再発行にも対応する。
- コンセプト：**「誰でも、簡単に、きれいな領収書を作れる」**

設計の優先方針：

1. 会員登録せずにすぐ利用できる。
2. 普段は必要最低限の入力だけで作成できる。
3. 詳細機能は必要なときだけ表示する。
4. PDF・印刷品質を重視する。
5. 企業・個人・自治会・イベントなど幅広い用途に対応する。
6. 利用者の情報とプライバシーを保護する。
7. 無料サービスとして運営コストを抑える。
8. 将来的な機能追加を妨げない設計とする。

# 2. 開発環境・運用方針

- 基盤：GitHub、Orca、TSS AI Core、Claude Code、Codex、Cloudflare（tss-dev-os は自動導入しない：TSS AI Core R-10）
- 税務・法務の判断は公式資料で検証する。AIの判定だけで法的適合性を保証しない。
- 専門家の人数を増やすこと自体を目的とせず、既存のTSS AI Coreの仕組みを活用する。
- 軽微な判断は自律的に進める。重要な仕様変更・コスト発生・外部公開は人間の承認を得る。
- 実装後は独立した品質レビューを実施する。顧客価値と使いやすさを評価する。

# 3. 確定済みの機能要件

明確な矛盾・技術的制約・法令上の問題がない限り、再度の選択質問を行わない。

## 3-1. 利用者区分

### ゲスト利用
- 会員登録不要。領収書の作成・PDF保存・印刷が可能。一括発行も可能。
- 発行者と宛先は直接入力。
- 領収書番号は省略を基本とし、必要な場合のみ手入力。
- 発行履歴はサーバーに保存しない。
- 利用者が明示的に選択した場合のみ、ブラウザー内に下書きを保存できる。下書きの呼び出し・削除に対応。

### 無料会員
- メール認証コードによるログイン。Googleアカウントによるログイン。
- 発行者マスター管理。宛先マスター管理。
- 発行履歴の保存。発行者ごとの領収書番号自動連番。
- 過去の領収書の検索・再印刷。
- CSVインポート・エクスポート。データの一括書き出し。
- 1日100件の発行上限。
- 会員が削除・退会するまでデータを継続保存する方針。

## 3-2. 領収書入力

基本入力項目：発行者名／宛名／敬称／領収金額／但し書き／領収日

詳細入力項目：発行者住所・郵便番号／電話番号／インボイス登録番号（任意）／領収書番号／発行日／取引日／支払方法／消費税の詳細／備考／ロゴ／印影／デザイン／印刷形式／収入印紙貼付欄

### 日付
- 領収日は当日を初期値とする。発行日は必要な場合のみ変更可能。取引日は領収日を初期値とする。
- 領収日変更時には、未編集の取引日を連動させる。取引日を個別に変更した場合はその値を維持する。

### 宛名
- 宛名が未入力の場合は警告する。一般領収書では確認後に空欄発行も可能。
- インボイスとして発行する場合は必要な記載事項を確認する。

### 支払方法
任意入力。領収書への表示・非表示を選択できる。現金／銀行振込／クレジットカード／電子マネー／QR決済／その他

## 3-3. 消費税・インボイス

### 消費税入力
シンプル入力：金額入力／税込・税抜の切替／税率選択／消費税額の計算
詳細入力：複数明細／10％・軽減税率8％の混在／税率別対象金額／税率別消費税額／非課税等の区分
日本のインボイス制度に対応する端数処理・記載方法を確認すること。

### 領収書の3モード
1. 一般領収書
2. 適格請求書対応
3. 適格簡易請求書対応

- インボイス登録番号は必須としない。登録番号がない利用者も一般領収書を作成できる。
- 適格請求書として必要な記載事項に不足がある場合は、インボイスとしての発行を止め、修正または一般領収書への切り替えを案内する。
- 適格簡易請求書では、対象事業であることの確認を必須とする。
- 各モードの記載要件は国税庁の公式情報で検証する。

## 3-4. 領収書デザイン
- 3種類：シンプル／ビジネス／カジュアル。初期値はシンプル。
- テーマカラー変更可能。発行者ごとにデザイン設定を保存。
- 会社ロゴ表示可能。領収印の表示・非表示が可能。
- 発行済み領収書は、発行時点のデザインを再現できるようにする。

## 3-5. 領収印（角印）
- 2方式：①印影画像のアップロード ②アプリ内での領収印（角印）作成
- 角印作成：文字入力・朱色・サイズ・配置などを設定。
- 背景透過画像に対応。発行者ごとに保存・再利用。領収書上の位置・大きさを調整可能。
- 法的な電子署名や本人認証機能とは区別する。

## 3-6. 印刷形式
4種類：①A4：領収書1件 ②A5：領収書1件 ③A4：領収書2件を上下に配置 ④A4：領収書＋控え

- 実寸印刷に対応。PDFと実際の印刷結果の一致を重視。
- 印刷時に入力フォームなどの画面要素を出力しない。改ページによる崩れを防止。
- A4の2枚分割では裁断ガイドの表示・非表示を選択可能。
- 奇数件の場合、最終ページの下半分を空欄とする。
- 領収書＋控えでは同一番号・同一金額を使用。控えには発行担当者・入金方法・管理用備考などを記載可能。
- A4を二等分した場合と規格A5との寸法差にも注意する。

## 3-7. 収入印紙
- 貼付欄の表示・非表示を選択。
- 金額・取引内容・交付方法に応じて印紙税を案内。紙での交付と電子交付を区別。
- 必要となる印紙税額の目安を表示。判断できない場合は利用者に確認を促す。
- 印紙税の納付・貼付・消印はアプリでは代行しない。
- 税額表と判定条件は、法令改正に対応できる構造とする。

## 3-8. 一括発行
3方式すべてに対応：①登録済み宛先マスターから選択 ②CSVファイルの読み込み ③Excel等から宛先を直接貼り付け

- 複数宛先に同じ金額を設定。発行者・但し書き・日付などを共通設定。
- 発行前に宛先一覧を確認。重複・空欄を警告。並び順を確認・変更可能。
- 選択した印刷形式で一括PDF生成。
- 取り込んだ宛先を、マスターに保存するか選択可能。
- ゲストの場合、宛先はサーバーに保存しない。

## 3-9. 発行者・宛先マスター

### 発行者マスター（複数登録）
発行者名／住所・郵便番号／電話番号／インボイス登録番号／ロゴ／印影／デザイン設定／よく使う但し書き／領収書番号の接頭辞・連番／既定の印刷形式／税額計算関連設定

### 宛先マスター
同一会員が登録するすべての発行者で共通利用。宛先名／敬称／郵便番号・住所／担当者名／グループ／宛先コード／メモ。他の会員とはデータを分離する。

### CSV管理
CSV一括登録／既存データの更新／取り込み前プレビュー／宛先コードなどによる照合／重複候補の確認／文字化け・不正値対策／CSVエクスポート／CSVテンプレート提供。名前だけの一致で自動上書きしない。

## 3-10. 領収書番号・発行履歴
- 発行者ごとの独立連番。一括発行でも1件ごとに番号付与。
- プレビューでは番号を確定しない。発行確定時に採番・履歴保存。
- 発行済み番号は再利用しない。再印刷では新番号を発行しない。
- 発行者情報やデザインが後から変更されても、発行時点の内容を保持。

### 発行取消
個別取消／一括取消／取消理由記録／操作日時・操作者記録／取消済みの履歴保持

### 訂正再発行
新しい領収書番号を発行。元の領収書と関連付け。訂正前後の内容を保持。訂正理由を記録。

### 履歴管理
発行者別／日付別／宛先別／状態別／一括発行グループ別／PDF再出力／CSV書き出し

## 3-11. データ保存
無料会員のデータは、本人が削除・退会するまで継続保存する方針。履歴保存／データ一括書き出し／ZIPによる取得／CSV・PDF出力／アカウント削除／データ削除／バックアップ／復元手順。税務上の法定保存義務については、サービスの保存機能と区別して案内する。

## 3-12. 利用制限
無料会員の発行上限は1日100件。会員内の全発行者を合算。一括発行は宛先1件につき1件。再印刷は件数に含めない。訂正再発行は新規発行として計算。取消によって使用済み件数は戻さない。日次集計は日本時間を基本案とする。
ゲストについては同等の会員別日次制限を保証できないため、適切な濫用対策を別途検討する。

# 4. UI/UX要件

基本構成：**1画面完結型＋詳細設定折りたたみ＋リアルタイムプレビュー**

- パソコン：左に入力フォーム、右に領収書プレビュー。
- スマートフォン：縦並び表示。入力とプレビューの切替・スクロール操作を最適化。
- 基本画面はシンプルに。詳細機能は必要な場合のみ開く。入力内容は即時にプレビューへ反映。
- エラー・警告を分かりやすく表示。一括発行でも迷わず操作できる。印刷時の仕上がりを重視。
- 専門用語をできるだけ利用者向けの日本語に置き換える。

# 5. 開発フェーズ

## Phase 1：ゲスト版（最優先）
1画面入力／リアルタイムプレビュー／一般領収書・適格請求書・適格簡易請求書／消費税計算／印紙税案内／3種類のデザイン／4種類の印刷形式／角印作成・画像アップロード／CSV・貼り付けによる一括発行／PDF生成・印刷／任意のブラウザー内下書き保存

会員登録・サーバー側の発行履歴保存は行わない。最初は本人だけが動作検証する。Cloudflareへ限定的にテスト公開し、実際の印刷結果を確認する。

## Phase 2：無料会員機能
メール認証コード／Googleログイン／発行者マスター／宛先マスター／CSV登録・更新／発行者別連番／発行履歴／個別取消・一括取消／訂正再発行／データ書き出し／1日100件制限

## Phase 3：正式公開
運営者管理画面／アクセス権限管理／不正利用対策／バックアップ・復元／退会処理／プライバシーポリシー／利用規約／運営監視／費用監視／障害対応

## 将来の機能
複数会員による発行者の共同管理（初回開発には含めないが、拡張可能な設計とする）。

# 6. 技術方針

Cloudflareを基本の公開基盤とする。想定構成（候補。Orca側で最新仕様・実現性・運用コストを検証して確定）：

- Cloudflare Workers / Static Assets
- React等のフロントエンド
- D1：将来の会員データ・マスター・発行履歴
- R2：必要に応じた画像・ファイル保存
- 認証基盤：メール認証コード・Googleログイン
- GitHub：ソースコード・仕様管理

特に検討すること：
1. ブラウザー内PDF生成とサーバー側PDF生成の比較
2. 日本語フォントの埋め込み・文字化け対策
3. 印影・ロゴを含むPDFの品質
4. 100件程度の一括発行時の処理性能
5. 4種類の用紙サイズ・改ページの再現性
6. D1での連番採番と同時発行の整合性
7. 将来の会員管理に対応できるデータ構造
8. 無料運営時のコスト・利用上限
9. ゲストの個人情報をサーバーへ送信しない方式
10. スマートフォンでの操作性と印刷環境の制約

過剰なインフラや不要な外部サービスは採用しない。

# 7. セキュリティ・プライバシー

- 他の会員のデータへアクセスできない。
- 運営者は通常、領収書内容を閲覧しない。サポート時のみ、本人の明示的な許可に基づいて限定閲覧。
- アクセス範囲・期限・操作履歴を記録。サポート担当者による領収書の直接変更は禁止。
- 認証・認可・データ分離を適切に実装。バックアップと復元手順を整備。
- 個人情報の削除・退会に対応。公開前にセキュリティレビューを実施。

# 最重要指示

- これまでの要件定義を尊重し、決定済みの事項を何度も質問し直さない。
- 利用者にとって価値のない機能追加や、過剰な設計を避ける。
- **「誰でも簡単に領収書を作れる」という本来の目的を最優先する。**
