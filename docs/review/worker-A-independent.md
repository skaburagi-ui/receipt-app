## 1. 欠けると致命的な論点（重要度順・14件）

### 1. 利用者像・成功基準・差別化が要件にない
- 観点：A/G　重要度：**致命**　節：§1、§5
- 問題：目的は「誰でも」だが、誰が最初の利用者か（個人事業主／自治会・イベント／小規模店／経理担当）が未定。そのため Phase 1 の取捨選択ができず、全利用者向けの機能が全部入りになっている。無料の領収書作成ツールは既に多数ある（freee等の請求書サービスにも領収書機能がある）が、競合との違いの記述がない。出典が「ChatGPTとの対話」であり、実利用者への確認が見当たらない。
- 推奨：Phase 1 の前に、主要利用者を1〜2種に絞る。3〜5人に現在のやり方（Excel／手書き／既存サイト）を聞く。「入力開始から印刷まで何分か」「印刷が実寸でずれずに出るか」などの合否基準を決める。
- 証拠：【推測】（競合の存在は一般知識で、URLは未確認）

### 2. 印紙税の「判定」機能（§3-7）は責任が重く、入力項目も未定義
- 観点：E/G　重要度：**致命**
- 問題：「金額・取引内容・交付方法に応じて税額を案内」するが、判定に必要な入力（取引内容・営業に関するか否か・紙か電子か）が§3-2の入力項目に存在しない。国税庁 No.7105（検索要約）では領収書は第17号文書で、売上代金5万円未満は非課税、5万円以上100万円以下は200円。消費税額が区分記載されていれば税抜で判定する。電子データのみの交付は課税文書の作成にならないという回答事例もある（上記福岡国税局）。ただし印刷した時点で紙交付になる。つまり判定ロジックは「受取書の種類×金額×税区分×交付方法」で、誤案内は利用者の過少納税につながる。
- 推奨：Phase 1 は静的な注意表示に絞る。「紙で渡す場合、5万円以上は収入印紙が必要になることがあります。詳しくは国税庁 No.7105」と案内し、**金額の自動判定はしない**。貼付欄の表示・非表示だけ実装する。税額表の構造化（§3-7 末尾）は Phase 2 以降。「営業に関しない受取書は非課税」という点は自治会・個人用途では重要だが、**原文は未確認**。
- 証拠：【代理】（検索要約。原文ページ未読）

### 3. インボイス3モードの記載要件・端数処理の正しさを検証する手段がない
- 観点：E　重要度：**致命**　節：§3-3
- 問題：①適格簡易請求書の対象は、小売業・飲食店業・写真業・旅行業・タクシー業・駐車場業（不特定多数向け）とこれに準ずる事業（国税庁Q&A、検索要約）。判定はアプリではできないため、チェックボックスの自己申告になる。②簡易請求書は「適用税率」か「税率ごとの消費税額」のどちらか一方でよく、宛名省略も可（同Q&A）。しかし要件には「どの項目を必須にするか」の一覧がない。③端数処理は「税率ごとに1回」が原則（No.6371原文は未確認、二次情報のみ）。明細ごとに丸めると不適格になる。要件は「確認すること」としか書いていない。④税抜／税込が明細ごとに混在する場合の扱いが未定義。
- 推奨：国税庁の例題を使った自動テストを、実装前の受入基準にする。「適格請求書」モードを先に作る。通常の適格請求書は、簡易請求書の対象事業でも発行できる（国税庁Q&A、検索要約）ので、簡易モードは後回しにできる（§3参照）。
- 証拠：【代理】＋端数処理は二次情報

### 4. 偽造・不正利用の対策方針がない（会員登録なし＋任意の発行者名＋角印）
- 観点：F/E　重要度：**致命**（正式公開前）　節：§3-1、§3-5、§5 Phase 3「不正利用対策」
- 問題：本人確認なし・履歴なしで、他人の社名と角印画像を入れた「きれいな領収書」が作れる。経費の不正請求や詐欺に使われる恐れがある。Phase 3 に「不正利用対策」とあるが、限定テスト公開（Phase 1）の時点で既に公開される。§3-12 も「ゲストの濫用対策は別途検討」とだけ記載。
- 推奨：Phase 1 の公開前に最低限を決める。①利用規約と画面上の注意（「発行者本人が使うこと」）。②ゲストの非対策範囲の明示。③「透かし」や「作成ツール名のフッター」を入れるかの方針（見た目とのトレードオフ。人間の判断事項）。
- 証拠：【推測】

### 5. 「無料運営」と Cloudflare 無料枠が噛み合わない箇所がある
- 観点：B/G　重要度：**致命**　節：§1-7、§3-1、§3-12、§6
- 問題（いずれも検索要約で確認）：
  - **メール認証コード**：Email Sending は2026年4月に公開ベータ。任意の宛先への送信は **Workers Paid プランが必要**（無料プラン不可）。有料プランは月3,000通まで込み、超過は1,000通あたり$0.35。→「メールOTPログイン＋無料運営」はそのままでは成立しない。
  - **サーバー側PDF**：Browser Rendering は無料プランで**1日10分**。Workers の CPU は無料で10ms。→ サーバー側PDF生成は無料枠では非現実的。ブラウザー内生成が必須（§6-9とも整合）。
  - **D1**：無料枠の読み取り・書き込み超過時はクエリが失敗する仕様が2026-09-01から有効。書き込みは1日10万行（インデックスも加算）、DBサイズは500MB（第三者情報、公式は未確認）。
- 推奨：Phase 1 はサーバー処理ほぼ無し（静的配信＋ブラウザー内PDF）で成立させる。Phase 2 の認証は Googleログインを先に実装する。メールOTPは有料化の判断後。無料枠超過時の挙動（停止／新規発行のみ停止）と費用上限を人間が決める。
- 証拠：【代理】

### 6. 画面プレビュー・ブラウザー印刷・PDF の3経路が不一致を起こす
- 観点：D/B　重要度：**致命**　節：§3-6、§6-1・2・3・5
- 問題：「リアルタイムプレビュー（HTML）」「印刷（ブラウザーのCSS印刷）」「PDF」を別々に実装すると、改ページ・フォント・実寸が3通りに食い違う。「PDFと印刷の一致を重視」（§3-6）と矛盾しやすい。さらに日本語フォントの埋め込み（巨大なフォントのサブセット化）と、**100件一括のブラウザー内PDF生成**は、特にスマホでメモリ不足になる恐れがある。人名に多い異体字（髙・﨑・𠮷・辻の字形差など）がフォントに含まれるかの確認も要る。
- 推奨：出力経路を一本化する。例：生成したPDFだけを正本にして、プレビューもPDF描画にする（または印刷専用CSSのHTMLを正本にして、PDFは「ブラウザーのPDF保存」に任せる）。最初に1〜2日の技術検証（スパイク）を行い、①日本語＋異体字、②100件のメモリと時間、③iOS/Android/PCでの印刷、を確認してから §6 を確定する。
- 証拠：【推測】（構造上の一般的リスク）

### 7. 用紙・実寸・「2件配置」「控え」の定義が曖昧
- 観点：D/A　重要度：高　節：§3-6
- 問題：①「A4：領収書2件を上下に配置」は、同一内容の複写なのか、別々の2件なのか不明（「奇数件なら下半分を空欄」は別々の2件を示唆）。単件作成のときの扱いも不明。②「A5：領収書1件」はA5用紙に出すのか、A4用紙にA5サイズで出すのか不明。③「A4二等分とA5の寸法差に注意」とあるが、ISO 216の寸法（A4=210×297mm、A5=148×210mm）から、二等分は210×148.5mmで差は約0.5mm。実務上の問題は寸法差より**プリンターの非印字領域と拡大縮小設定**。④スマホからの印刷は、実寸保証が難しい。
- 推奨：4形式を「用紙」「面付け（1面／2面）」「中身（同一／別件／本券＋控え）」の3軸で定義し直す。実寸に印刷するための案内（拡大縮小「100%」）とテスト印刷用ページを用意する。対応する印刷環境（OS・ブラウザー・代表的なプリンター）を決める。
- 証拠：【推測】（寸法は算術。ISO 216 の資料URLは未確認）

### 8. 「誰でも簡単」に反する複雑さ（用語と選択肢の多さ）
- 観点：C　重要度：高　節：§3-2、§3-3、§3-6、§4
- 問題：①日付が「領収日・発行日・取引日」の3つ。一般利用者には違いが分からない。インボイス上は取引年月日が必要（検索要約）。②「一般／適格請求書／適格簡易請求書」はそれ自体が専門用語で、§4の「専門用語を平易に」と矛盾。③ゲストは「明示的に選んだときだけ下書き保存」（§3-1）なので、**発行者名・住所・振込先などを毎回入力し直す**ことになる。実際に反復して使う人ほど不便。④スマホでの「入力⇔プレビュー切替」のUIは未設計。
- 推奨：日付は既定で1つ（領収日）にして、他は詳細に隠す。モードは質問形式にする（「インボイス登録番号をお持ちですか？」→持っていれば適格請求書、無ければ一般）。ゲスト向けに「この端末に発行者情報を記憶する」を**オプトイン**で用意する。4形式は初期値を1つにして、選択はプレビュー下に置く。
- 証拠：【推測】

### 9. 「発行確定」「再現」「連番」の仕様が穴だらけ
- 観点：A/H　重要度：高　節：§3-4、§3-10、§3-12
- 問題：①「発行確定」の瞬間が未定義。ブラウザーは印刷ダイアログのキャンセルを検知できないため、「印刷＝発行」にはできない。**ボタン操作で確定**と定義する必要がある。②「発行時点のデザインを再現」には、入力値のスナップショットに加えて**テンプレートのバージョン**が要る。コード更新で過去の領収書の見た目が変わる。③発行者を削除して同じ接頭辞で作り直すと、番号が再利用される（§3-10「再利用しない」と矛盾）。④一括発行の途中失敗で欠番が出た場合の扱い、100件で日次上限を超える場合に全件拒否か部分発行かが未定義。⑤同時発行の整合性は D1 で単一SQL（`UPDATE … SET n=n+1 RETURNING`）＋バッチで実現できる見込みだが、無料枠のクエリ数上限（第三者情報で50）に注意（公式未確認）。
- 推奨：スナップショット＋テンプレートバージョンを保存する設計を、Phase 1 のデータ型から取り入れる（保存先がブラウザーでも同じ形）。発行者は「論理削除のみ」にして、番号の払い出し履歴を残す。
- 証拠：【推測】（D1の挙動は公式未確認）

### 10. 無期限保存＋無料＋1日100件はコストが青天井
- 観点：G/B　重要度：高　節：§3-11、§3-12、§1-7
- 問題：「会員が退会するまで継続保存」は、無料の長期ストレージ契約になる。1人1日100件の上限は、1か月で3,000件、D1の書き込み（インデックス込みで数倍）は無料枠を超え得る。ロゴ・印影の画像（R2）も無期限に増える。休眠会員の削除方針がない。PDFを保存せず再生成する方式かどうかも未定。
- 推奨：①PDFは保存せず、スナップショットから再生成する。②画像サイズ上限を設ける。③休眠アカウント方針（例：一定期間ログインが無ければ通知後に削除）を人間が決める。④上限100件の根拠（コスト？濫用？）を明確にする。
- 証拠：【代理】（無料枠）＋【推測】（利用量）

### 11. Phase 2 で個人情報を預かるのに、法務・運用の整備が Phase 3
- 観点：F/A　重要度：高　節：§5、§3-11、§7
- 問題：バックアップ・退会処理・プライバシーポリシー・利用規約が全て Phase 3。しかし Phase 2 でメール・宛先（個人情報）をD1に保存する。Phase 1 の「限定テスト公開」でも、利用規約（税務判断の免責）が必要。また、アクセス解析・エラー収集・外部フォント等を入れると、電気通信事業法の外部送信規律（通知・公表）の対象になり得る（総務省資料、検索要約。無料サービスなら免除、という記述は見当たらなかった）。
- 推奨：Phase 2 は「非公開（招待制）」と明記する。Phase 1 公開時に、簡易な利用規約・プライバシー表示（「入力内容は送信されません」の範囲を含む）を出す。外部ツールは最初は入れない。
- 証拠：【代理】

### 12. 発行者・宛先の所有モデルが将来の「共同管理」と衝突する
- 観点：H　重要度：高　節：§3-9、§5「将来の機能」
- 問題：宛先マスターは「同一会員が登録する全発行者で共通」＝会員が所有者。将来、複数会員で発行者を共同管理するなら、所有者は「会員」ではなく「発行者（または組織）」になる。後からだと、D1のスキーマ変更・データ移行・認可ロジックの作り直しが必要。「操作者を記録」（§3-10）は、共同管理がなければ意味が薄い。
- 推奨：Phase 2 の最初から `workspace`（会員1人につき1つ自動作成）を所有者にし、会員は `membership` で結ぶ。UIは単独利用のまま。ただし**過剰設計は避け**、権限の細分化は将来に回す。
- 証拠：【推測】

### 13. ゲストの「サーバーに送らない」を保証するための条件が未記載
- 観点：F/B　重要度：中〜高　節：§3-1、§6-9、§7
- 問題：①アクセス解析・エラー収集・外部フォントCDNが入力値や端末情報を送らないか。②ブラウザー保存（下書き）は平文で、共用PCでは他人に見える。印影画像などは localStorage の容量（一般に約5MB、仕様上の目安）を超えやすいので、IndexedDB を想定すべき。③ゲスト下書きの「削除」操作とユーザーへの注意表示。
- 推奨：Phase 1 は外部通信ゼロ（自前ホスティングのフォント・解析なし）を受入基準にする。下書き保存時に「この端末に保存されます。共用PCでは使わないでください」と表示する。
- 証拠：【推測】

### 14. CSV・取消・訂正の意味づけに法令・運用上の穴
- 観点：A/E/F　重要度：中　節：§3-9、§3-10
- 問題：①CSV：文字コード（Excelで保存するShift_JIS／UTF-8 BOM）の判別、エクスポート時のCSVインジェクション（`=`・`+`・`@` で始まるセル）が未記載。②「取消」はアプリ内の記録に過ぎず、相手に渡した領収書は無効にならない。再印刷時に「取消済み」を表示するのかが未定。③インボイスの訂正（修正した適格請求書）に必要な記載（元の書類との関連付け）は、**要件の確認が必要だが、今回は未確認**。
- 推奨：CSVは UTF-8（BOM付き）と Shift_JIS の両対応、件数・サイズ上限、セルの無害化を要件に追加する。取消済みの再出力には「取消済み」の表示を入れる。訂正再発行は、インボイスモードでの記載要件を国税庁資料で確認してから設計する。
- 証拠：【推測】（③は未確認）

## 2. 要件内の矛盾・曖昧箇所

| 節 | 内容 |
|---|---|
| §3-1 / §3-8 / §3-10 | ゲストの一括発行時に領収書番号をどうするか未定義（「手入力のみ」と「一括は1件ごとに採番」が会員前提）。「控えは同一番号」（§3-6）との整合も不明。 |
| §3-2 日付 | 発行日の既定値（領収日と同じか）が未記載。3つの日付の違いが利用者に分かりにくい。 |
| §3-2 / §3-3 | インボイス登録番号は「任意」だが、適格請求書・簡易請求書モードでは実質必須。必須条件の一覧（モード別）が無い。 |
| §3-3 | 税抜／税込が明細ごとに混在する場合、端数処理の単位（税率ごとに1回）と丸め方式（切捨て・四捨五入・切上げ）を誰が選ぶか未定義。「非課税等の区分」の範囲も曖昧。 |
| §3-6 | 「2件上下配置」が複写か別件か不明。「A5：1件」の出力用紙が不明。A4二等分とA5の寸法差の注意（約0.5mm、実務上は余白と拡大縮小の問題）。 |
| §3-7 | 印紙税の判定入力（取引内容・交付方法）が§3-2に存在しない。 |
| §3-10 | 「発行確定時に採番」の「確定」の定義がない。ゲストには「確定」の概念自体がない。 |
| §3-10 / §3-9 | 発行者を削除（退会時データ削除含む）すると、「番号は再利用しない」「取消済みも履歴保持」と矛盾し得る。 |
| §3-11 / §5 | 保存・バックアップ・退会は§3-11で要件化されているが、Phase 3 に配置。Phase 2 で個人情報を預かる期間が空く。 |
| §3-12 | 「日本時間を基本案」が未確定。一括発行が上限（100件）を超える場合の挙動（全件拒否／部分発行）未定義。上限100の根拠がない。 |
| §4 / §3-3 | 「専門用語を平易に」と言いながら、モード名が専門用語（適格請求書等）のまま。 |
| §7 / §5 Phase 3 | 運営者は「通常閲覧しない」が、技術的にはD1の平文を閲覧できる。サポート時の限定閲覧機能は大きな開発で、方針と実装のギャップが明記されていない。 |
| §3-9 / 将来 | 宛先マスターの所有者（会員）と、将来の共同管理（発行者単位）の矛盾（論点12）。 |
| §6 | 候補構成のため確定していないが、「認証基盤」の具体案が無く、Cloudflare無料枠でのメール送信が成立しない（論点5）。 |

## 3. Phase 1 から外す／簡素化を検討すべき機能

| 機能 | 提案 | 理由 |
|---|---|---|
| 適格簡易請求書モード（§3-3） | **後回し**。Phase 1 は「一般」と「適格請求書」の2つ。 | 通常の適格請求書は、簡易請求書の対象事業でも発行できる（国税庁Q&A、検索要約）。簡易は対象事業の自己申告と記載要件の分岐が増え、検証コストが大きい。利用者が「宛名なしで出したい店舗」に多い点は【推測】なので、需要を見て追加。 |
| 印紙税の自動判定（§3-7） | **静的な注意表示＋貼付欄のON/OFF**のみ。 | 論点2。誤案内のリスクが高く、入力項目が未定義。 |
| 3種類のデザイン＋テーマカラー（§3-4） | Phase 1 は**1デザイン＋テーマカラー**。 | 3デザイン×4形式×3モードで検証パターンが爆発する。「シンプル」が初期値で、他は需要不明。 |
| 4つの印刷形式（§3-6） | **A4（1件）／A4（領収書＋控え）／A4（2件）**を先に。A5単体は後。 | A5用紙は家庭用プリンターで扱いにくい。実測してから追加。 |
| アプリ内の角印作成（§3-5） | Phase 1 は**画像アップロードのみ**。作成機能は Phase 1.5。 | 作成機能は文字フォント・配置・透過処理のUIが重い。ただし「印影画像を持たない人」の多さは【推測】なので、Phase 1.5 で早めに入れる価値あり。 |
| 一括発行（CSV・貼り付け・並べ替え、§3-8） | Phase 1 の**後半（1.5）**。まず単票で実寸印刷の品質を検証。 | 100件のブラウザー内PDF（メモリ）とゲストの番号問題（論点9）が未解決。CSV読込と貼り付けは同じ解析部品で作れる。 |
| ゲストの「下書き保存・呼出・削除」（§3-1） | 簡素化：**自動保存せず、発行者情報の記憶（オプトイン）**を優先。 | 下書きより、毎回の発行者再入力の解消が価値が高いと推測（論点8）。 |
| 一括取消・CSV更新の照合（Phase 2） | Phase 2 後半へ。 | 単票の発行・履歴・再印刷が先。 |
| サポート時の限定閲覧機能（§7） | **作らない**（本人が書き出したデータを共有してもらう運用）。 | 期限・範囲・操作履歴の実装は重く、個人開発規模に不釣り合い。 |
| 運営者管理画面の大半（Phase 3） | 最小限（利用状況・停止）のみ。 | 無料サービスの運用負荷を抑える。 |

## 4. 発注者（人間）が判断すべき事項

決定済み事項は聞き直さない。ただし、矛盾・法令・コスト上の理由がある項目は「例外」と付記。

1. **主要利用者**：Phase 1 の最優先は誰か（個人事業主／自治会・イベント／小規模店／経理担当）。成功の基準は何か。
2. **Phase 1 の削減案（§3の表）を承認するか**。特に適格簡易請求書・角印作成・3デザインの後回し。
3. **偽造・不正利用への姿勢**：透かしやフッター表示を入れるか、規約と注意書きのみにするか。
4. **費用上限**：月いくらまで許容するか。有料の Cloudflare プランやメール送信サービスを使う前提か（論点5）。無料枠超過時は新規発行を止めるか。
5. **（例外：コスト）無期限保存の方針**：休眠アカウントの削除、保存件数・画像容量の上限を設けてよいか。
6. **（例外：法令リスク）印紙税の自動判定をやめ、静的な注意表示にしてよいか**。
7. **1日100件の根拠**：コストの上限か濫用対策か。一括が100件を超える場合の挙動。ゲストの一括上限は何件か。
8. **運営主体・責任の所在**：利用規約・プライバシーポリシーの名義、免責の範囲、問い合わせ窓口。
9. **アクセス解析の利用有無**（外部送信規律・「サーバーに送らない」との関係）。
10. **「取消」の意味**：アプリ内記録のみで、再出力時に「取消済み」を表示してよいか。
11. **印刷の対応範囲**：スマホからの印刷は「保証」か「PDF保存のみ案内」か。対象のOS・ブラウザー・プリンター。
12. **ゲストが発行者情報を端末に記憶する機能を認めるか**（プライバシーとの兼ね合い）。

## 5. 特に良い判断（変えるべきでない点・3つ以内）

1. **ゲストは会員登録・サーバー保存なし、会員機能は Phase 2 に分離**（§3-1、§5）。コスト・プライバシー・開発量のすべてを抑え、本来の目的「すぐ使える」に直結する。
2. **インボイス登録番号を必須にせず、要件不足のときは発行を止めて一般領収書へ誘導**（§3-3）。登録番号のない大多数の利用者を排除せず、誤った適格請求書の発行も防ぐ。
3. **番号ルール：プレビューでは確定しない／発行確定時に採番／再利用しない／再印刷は新番号なし／取消で件数を戻さない**（§3-10、§3-12）。後から変更しにくい中核の整合性を、先に固定している。

（補足：§2「税務・法務は公式資料で検証し、AIの判定だけで適合性を保証しない」も良い方針だが、**検証のための受入テスト基準が無い**点は論点3のとおり。）
