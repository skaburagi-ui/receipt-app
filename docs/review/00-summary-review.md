# 要件定義Ver.3.3 総合レビュー（統合報告）

- レビュー日：2026-11-05 ／ 対象：`docs/requirements-v3.3.md` ／ 状態：**要件レビュー段階（実装未着手）**
- 体制：司令塔（本書の統合）＋独立ワーカー4名（Orca Orchestration）。A=独立レビュー（原文のみ参照）、B=税務・法令、C1=Cloudflare・認証・コスト、C2=PDF・印刷。個別報告は同じ `docs/review/` にある。
- **証拠の区分（D-19）**：本レビューの根拠は【代理＝国税庁・Cloudflare等の公式資料】【実測＝Node上の使い捨て検証。モバイル・ブラウザー実機は未実施】【AI推測】である。**実際の利用者の声・行動データは、要件にも手元にもない。**
- 注意：AIによる検証であり、法的適合性の保証ではない。税務・法務の最終確認は税理士・弁護士が必要（H-01(c)）。

## ① 要件定義レビュー結果

分類：**問題なし**／**改善推奨**／**要修正**（法令・矛盾・技術事実と合わない）／**要判断**（人間の判断が必要）

### 観点別の結論

| 観点 | 結論 | 要点 |
|---|---|---|
| A 整合性 | 要修正 | 3モードと登録番号欄の関係、日付の意味、ゲスト一括発行の番号、「発行確定」の定義、印紙税の入力項目欠落 |
| B Cloudflare実現性 | 改善推奨 | Phase 1は無料で成立。Phase 2はメール送信（独自ドメイン前提）とD1無料枠（全体停止リスク）が壁 |
| C UI/UX | 改善推奨 | モード名が専門用語。日付3種・4印刷形式・3デザインの選択肢過多。ゲストは発行者情報を毎回再入力になりやすい |
| D PDF・印刷 | 要修正（§3-6） | 「A4二等分」は210×148.5mmでA5縦ではない。A5の向きが未定。実寸は閲覧アプリ設定に依存し完全には保証できない |
| E 税務・法令 | 要修正 | 一般モードの登録番号欄は誤認表示の恐れ。適格請求書は宛名必須。端数処理は確定できる。印紙税は判定入力が不足 |
| F セキュリティ | 改善推奨 | 「運営者は閲覧しない」は技術的強制でなく運用ルール。偽造・不正利用の方針なし。規約・免責がPhase 3では遅い |
| G 工数・コスト | 要判断 | Phase 1は規模が大きい。範囲は変えず、内部で段階リリースにすることを推奨 |
| H 拡張性 | 改善推奨 | 所有モデルを「会員」でなく「発行者／作業領域」にする。テンプレート版数の保存 |

### 節ごとの判定

| 節 | 判定 | 理由・出典 |
|---|---|---|
| §3-1 ゲスト：登録不要・サーバー非保存 | **問題なし** | 最も良い判断。変更しない（A・C1・C2で一致） |
| §3-1 ゲスト：発行者情報の再利用 | 改善推奨 | 下書き保存に発行者情報を含め「毎回入力しない」導線にする（A#8、AI推測） |
| §3-1 無料会員（メールOTP＋Google） | 要判断 | Cloudflare自身のメール送信はWorkers Paid限定β。無料で行うならResend（日100通）＋独自ドメイン（C1、公式確認） |
| §3-2 日付の連動 | 改善推奨 | 適格モードの「年月日」は**取引日**（B、公式）。領収日との違いをUIで説明 |
| §3-2 宛名 | **要修正** | 適格請求書は宛名が法定記載事項（空欄・「上様」不可と読むのが自然だが公式の直接記述なし）。適格簡易は不要で「上様」可。一般は空欄可（B、問54・58-2） |
| §3-3 3モード | **要修正** | 名称でなく**記載内容**で法的性質が決まる（問25）。一般モードに登録番号欄があると意図せず適格簡易になり得る、または誤認表示になる（消法57条の5） |
| §3-3 端数処理 | **要修正（確定可能）** | 1書類につき税率ごとに1回、方法は任意、明細ごとの端数処理の合計は不可（問57） |
| §3-3 適格簡易の対象事業確認 | **問題なし** | 方向性は妥当。自己申告チェックとし、判定ロジックは持たない（B） |
| §3-4 デザイン／§3-5 角印 | 改善推奨 | 角印は「印鑑風（篆書体ではない）」と明記。縦書き・長音・括弧の字形に難所（C2） |
| §3-6 印刷形式 | **要修正** | 寸法定義・A5の向き・非印字領域（端から8mm以上内側）・実寸対策を追記（C2） |
| §3-7 印紙税 | **要修正** | 判定に必要な入力（課税/免税事業者・営業に関する受取・売上代金・交付方法・支払方法）が§3-2にない。紙に印刷して渡す場合の公式明文は未確認 |
| §3-8 一括発行 | 改善推奨 | ゲスト一括の領収書番号、上限件数、超過時の挙動が未定義（A） |
| §3-9 マスター／CSV | 改善推奨 | Shift_JIS・UTF-8 BOM対応、エクスポート時の数式文字無害化（全角＝＋－＠も）（C2） |
| §3-10 採番・履歴 | **問題なし**（中核）／要修正（周辺） | 採番ルールは良い。①「発行確定」をボタン操作と定義 ②テンプレート版数を保存 ③発行者は論理削除（番号再利用の防止）④訂正書面に元の日付・番号と修正箇所を印字 ⑤取消は内部管理表示（買手への法的効果なし）（A・B） |
| §3-11 保存 | 改善推奨 | 退会後もバックアップ（Time Travel 7日）に個人情報が残る。保持期間の明記と、復元後の退会者再削除手順（C1） |
| §3-12 利用制限 | 改善推奨 | 会員別100件だけでは**D1無料枠の全体停止**を防げない（C1）。日次の基準はJST（Cloudflareの日次クォータはUTC＝JST 9時リセットで別物） |
| §4 UI/UX | 改善推奨 | モード選択を質問形式に（「インボイス登録番号をお持ちですか？」）。スマホの入力⇔プレビュー切替は未設計 |
| §5 フェーズ | **要修正（配置）** | 利用規約・免責・出典表示はPhase 1の公開時点から必要。Phase 2は個人情報を預かるため非公開（招待制）を明記 |
| §6 技術 | **要修正** | Pages→Workers+Static Assets、メール送信手段の追加、認証ライブラリ選定、サーバー側PDFの不採用確定、pdf-lib不可（下記③） |
| §7 運営者の閲覧制限 | **要修正（表現）** | D1は管理者が全件閲覧可能。「運用ルール＋管理画面経由＋操作履歴」と明記 |

## ② 改善・追加提案（重要度順）

凡例：**【修正】**＝決定済み仕様が法令・矛盾・技術事実に合わないための修正案／**【具体化】**＝決定済み仕様の曖昧箇所を埋める案／**【新規】**＝AIからの新規提案（採否は発注者が決める）

### 高

1. **【修正】一般モードに登録番号欄を置かない。** 「適格請求書ではありません」を既定表示（OFF可）。「インボイス」「適格」の語は一般モードで使わない。税率別の税込合計の参考表示は許す案（案B）が推奨候補（買手の経過措置にも有利：問26-2）。ただし線引きは専門家確認が必要。
2. **【修正】適格請求書モードは、登録番号・宛名・取引日・税率別金額・税率別税額を必須にし、不足なら発行停止。** 適格簡易は対象事業の自己確認＋「税率または税額のどちらか」必須。適格系は「自分自身の登録番号です」の確認チェック必須（偽りの記載の防止）。
3. **【修正】端数処理を確定仕様に。** 書類×税率ごとに1回／税込は×10/110（8/108）、税抜は×10/100（8/100）／税込・税抜は書類内で統一／**マイナス明細（値引・返品）はPhase 1非対応**。Bが挙げた検証値（60,000円→5,454円、40,000円→2,962円、105円×3行→28円）をテスト仕様にする。
4. **【修正】印紙税は「目安／可能性／判断できません」の3段階表示にする。** 判定入力を§3-2へ追加。クレジット・QR決済・有価証券・不動産・営業か不明は「判断できません」。税額表は施行日・出典URL・確認日つきのデータにする。**紙で渡す場合と領収書PDFの電子交付の課税関係は公式に直接の明文がなく、税理士確認が前提。** 保守案は「静的な注意表示のみ」（A案）。→人間の判断（Q2）。
5. **【修正】Phase 1の公開時点から、免責・出典・保存義務の案内を表示する。** 文言案はB§13。写し（控え）の保存は利用者の責任であることを画面とPDFに明記する。
6. **【修正】§3-6の寸法を定義し直す。** ①A4縦 ②A5（向き要決定） ③**A4横分割**（210×148.5mm×2。A5縦ではない） ④同＋控え。重要要素は用紙端から8mm以上内側。実寸対策は、PDFの`PrintScaling=None`、試し刷りページ、利用者向け手順の3点。
7. **【具体化】PDFは、ブラウザー内で pdfmake＋静的TTFサブセット（Noto Sans/Serif JP）で直接生成する。** サーバー側生成は入力内容をCloudflareへ送るため方針違反、かつ無料枠でも現実的でない。**pdf-libは日本語サブセットでグリフ欠落（実測）のため使わない。**
8. **【修正】Phase 1の通信ゼロ要件。** 外部フォント・解析・エラー収集を入れない。CSP（`connect-src 'self'`）を要件化し、通信を観察して確認する（スパイクS11）。
9. **【修正】メール認証コードの手段を明記。** Cloudflare Email Sendingは有料限定βのため、Phase 2はResend無料（月3,000通・日100通・独自ドメイン必須）で開始し、送信は差し替え可能な抽象の裏に置く。日100通に達するとログイン不能になるため、Googleログイン併用・セッション長め・送信抑制を前提にする。

### 中

10. **【具体化】訂正再発行：** 訂正書面に元書類の日付・番号と修正箇所を印字する様式を追加（方式：全項目再記載型／修正箇所明示型。問33）。ゲストの訂正は元の日付・番号を手入力する方式。取消は「無効扱い（内部管理）」と表示し、買手への訂正書交付を案内する。
11. **【具体化】「発行確定」＝ボタン操作。** ブラウザーは印刷キャンセルを検知できない。入力値のスナップショット＋テンプレート版数を保存する設計をPhase 1のデータ型から取り入れる。
12. **【具体化】濫用対策（Phase 2）：** 新規登録のTurnstile、D1カウンタによるメール宛先・OTP試行制限、全体の日次書き込み監視と「新規登録の一時停止スイッチ」。無料D1の書き込み10万行/日を超えると全会員に影響する。
13. **【新規】所有モデル：** Phase 2の最初から発行者を「作業領域（会員1人につき自動作成）」の所有とし、将来の共同管理は`issuer_members`の追加で済む形にする。UIは単独利用のまま、権限の細分化はしない。
14. **【具体化】CSV：** UTF-8（BOM有無）／Shift_JIS／UTF-16を判別。貼り付けは区切りをタブに固定。件数・サイズ上限（暫定300行・5MB）。エクスポート時は`= + - @`とタブ・改行に加え全角`＝＋－＠`も無害化。
15. **【具体化】登録番号：** 入力を正規化（全角→半角、ハイフン除去）。「T＋13桁」の形式検証はローカルで行う。**チェックデジットで拒否してよいのは法人番号形式の場合のみ**（個人事業者の算式は公式未確認）。Web-API存在確認は、アプリIDの秘匿のためサーバー呼び出しが必要になり、ゲストの非送信方針と衝突するため**Phase 2以降**とする。
16. **【具体化】下書き保存：** 既定OFF、IndexedDB（画像含む）、「すべて削除」、30日で自動期限、ファイル書き出し／読み込み。**iOS Safariは約7日間操作がないと消える**ことがある旨を案内する。「暗号化されているから安全」とは案内しない。
17. **【具体化】フォントは自己ホスト、OFLライセンスのものだけ採用。** 旧字体・異体字（髙﨑邉𠮷等）は収録確認済み（Noto）。範囲外文字は警告し、勝手に正規化（髙→高）しない。IPAexはサブセット再配布の条件が多いので避ける。
18. **【新規】Phase 1の内部段階リリース（機能の削減ではない）：** 1a 単票（一般モード・A4/A5・PDF・実寸検証）→ 1b 適格2モード・消費税・印紙案内・角印・ロゴ → 1c 一括発行・残りの印刷形式とデザイン・下書き。本人が検証する前提なので、実寸印刷の品質確認を最初に終えられる。

### 低

19. **【新規】利用者像の確認：** 公開前に3〜5人へ現在のやり方（手書き・Excel・既存サイト）を聞く。現状は実際の声が一つもない。
20. **【具体化】「運営者は通常閲覧しない」を運用ルールと明記。** サポート時の限定閲覧は管理画面経由に限り、期間・範囲・操作履歴を記録する。実装はPhase 3で最小限にする。
21. **【具体化】罰則の表記は現行法の「拘禁刑」にする**（消法65条。「懲役」は古い）。

| 層 | Phase 1（ゲスト版） | Phase 2（会員） | Phase 3（正式公開） |
|---|---|---|---|
| 配信 | **Workers + Static Assets**（Workerコードなし）。Pagesは新規採用しない（公式が新規はWorkersを推奨） | 同一Workerに `/api/*` のみ追加 | 同左 |
| フロント | React＋Vite（SPA）。共通の「表示リスト」→SVGプレビュー／pdfmake PDF。Web Worker実行 | 同左 | ＋管理画面（ロール分離） |

| API／DB | なし（下書きはIndexedDB、ユーザー明示時のみ） | Hono＋D1（1DB）。Repository層で`user_id`を強制。画像はD1 BLOB（上限付き・重複排除） | 容量次第でR2。定期エクスポート |
| 認証 | なし | Better Auth 1.7系＋D1（不合格なら自前最小実装）。Arctic／Lucia／Auth.jsは非推奨・統合済みで不採用 | 管理者ロール、操作履歴 |
| メール | なし | Resend（独自ドメイン）。送信は差し替え可能な抽象の裏へ | 同左 |
| 濫用対策 | CSPのみ | Turnstile＋D1カウンタ＋WAF 1ルール | 監視・運用スイッチ |

**概算コスト（C1の試算。前提は仮定で、実測ではない）：**

| 規模 | 月額目安 | 最初に当たる壁 |
|---|---|---|
| Phase 1 | $0 | なし（静的アセットは無料・無制限）。独自ドメインなしでも `workers.dev` でテスト公開可 |
| 100人 | $0 | — |
| 1,000人 | $0〜25 | メール日100通／D1 500MB |
| 10,000人 | 約$18〜25 | Workers Paid $5＋メール有料 |

## ⑤ Phase 1の開発開始条件

### A. 実装前に確定すべき事項
1. 発注者の判断Q1〜Q10（下記）への回答、およびそれを反映した要件Ver.3.4。
2. 受入基準としての税務テスト仕様（端数処理の検証値、モード別の必須項目一覧）。
3. **スパイクの合格：** S1（日本語PDF生成・保存・Worker内動作）、S2（異体字）、S3（実寸印刷）、S10（Safari下書き消去。最長8日かかるので最初に着手）、S11（通信非送信）。不合格なら、ブラウザー印刷（CSS）方式への切替を検討する。
4. 免責・出典表示の文言（B§13を元に、税理士の確認を受ける）。

### B. テスト項目（最低限）
- **税計算：** 税込・税抜、10%／8%混在、切捨て・切上げ・四捨五入、明細合計と書類計算の差が出るケース。
- **モード制御：** 宛名・登録番号・取引日・税額のいずれかが欠けたとき適格系で発行停止。一般モードに登録番号欄が出ない。
- **印刷：** 4形式の寸法、奇数件の下半分空欄、裁断ガイドON/OFF、控えの同一番号。実機プリンター2台以上。
- **日本語：** 髙﨑邉𠮷㈱①〒を含む出力で豆腐・欠落がない。範囲外文字の警告。
- **一括：** 100件の生成時間・メモリ、CSV（CP932／UTF-8 BOM／UTF-16）、重複・空欄の警告。
- **通信：** 入力〜PDF生成〜下書きの間、外部通信ゼロ。
- **スマホ：** iOS Safari／Android Chromeでの保存・共有・印刷導線。

### C. 完成判定基準
1. 単票の入力開始からPDF保存まで、初めての人が迷わず数分以内に完了できる（本人検証＋可能なら数名）。
2. 実寸印刷で、100mm目盛が99〜101mm、A4二等分が148.5±1mm、8mm枠が欠けない。
3. 税務テストが全通過。不足時は適格系の発行が止まる。
4. 通信観察で個人情報を含む送信が0件。
5. 免責・保存案内・出典表示が画面とPDFにある。
6. 独立した品質レビューで、重大指摘が残っていない。
