## 2. 観点別の確認結果（指摘にしなかったものを含む）

**1. 税務ロジック**
- 端数処理：書類×税率ごとに1回（`tax.ts:28-67`）。整数の商と剰余で、浮動小数点の割り算なし。税込 ×10/110・×8/108、税抜 ×10/100・×8/100。国税庁の検証値（60,000→5,454／40,000→2,962／105×3→28）はテストで固定されている（`tax.test.ts:9-23`）。【事実】
- 境界：印紙税の税額表は、国税庁 No.7141 の本文と完全に一致した（5万円未満非課税／5万円以上100万円以下200円／…／10億円超20万円）。49,999／50,000／1,000,000／1,000,001 の境界テストあり。【事実：URL取得で照合】
- 消費税額の区分記載と判定金額：「課税事業者＋税額を書面に区分記載→税抜で判定／免税事業者→税込」は No.7124 の本文と一致。例（48,000＋4,800＝52,800→非課税）も一致。【事実】
- 登録番号：全角→半角・ハイフン・空白・日本語の除去、数字だけなら先頭に T。**個人事業者の番号をチェックデジットで拒否していない**（警告のみ）。公式例 `8700110005901` は警告なし。ただし M11 参照。
- 印紙税の断定語：「可能性があります」「目安」「判断できません」が使われ、断定語を禁じるテスト（`stamp.test.ts:170`）あり。クレジット・電子マネー・QR・営業か不明・課税事業者不明で結果が分かれる場合は `unknown`。根拠URLと確認日は全レベルに付く。【事実】
- 日付：`todayInJapan` はUTC+9で計算。領収日↔取引日の連動（未編集時のみ）は `defaults.ts:46-51` と `ui.test.tsx:132`。
- 仕様の穴：M2（適格簡易で課税なし）・M3（宛名の別表記）・M12（上限なし）。電子交付で `none`（「課税されない可能性」）を出すのは、根拠が注文請書の事例である旨が notes に書かれており、断定ではない。ただし判断は §4-2。

**2. 一般モードの法的安全性**
- 構造化された登録番号は、①入力欄を出さない（`IssuerSection.tsx:22`）、②`effectiveReceipt` で空にしてから検証・プレビュー・PDFへ渡す（`state.ts:78`、`App.tsx:22`）、③`buildSheet` が一般モードでは値を読まない（`buildSheet.ts:161`）の三重で遮断。モード切替の順序（適格で入力→一般へ戻す）・下書き復元（`replace` の後も `effectiveReceipt` が通る）・一括（`BulkDialog` の `base={eff}`）のいずれも、構造化欄からは出ない。【事実：コード読解＋既存テスト】自由記述欄だけが穴（M1）。
- 「適格」の語は、一般モードでは `showNotInvoiceNotice` の注記「適格請求書ではありません」にだけ出る（`buildSheet.ts:411`）。画面側の質問・チェックボックスには「インボイス（適格請求書）」の語があるが、これは操作画面であり出力ではない。
- 適格系の発行停止：`OutputBar.start()`・`BulkDialog.canGenerate`・各ボタンの `disabled` で止まり、Enterキー・フォーム送信経路は存在しない。下書き復元で迂回できるのは確認チェックのみ（M4）。フェイルオープンは L1・L2。

**3. プライバシー・外部通信**
- `src`・`index.html`・`public/_headers`・`dist/` を grep：実行時の通信は同一オリジンの `fetch('/fonts/…')` のみ。`dist` の `https?://` は、XML名前空間・RFC参照・国税庁へのリンクのみ（`<a>`、利用者のクリック時のみ、`rel="noopener noreferrer"`）。外部フォント・CDN・解析・`<link>`・`@import` なし。`eval`・`new Function`・WebAssembly も `dist` に無い。【事実】
- CSP（`public/_headers`）：`default-src 'self'; script-src 'self'; connect-src 'self'; object-src 'none'; frame-ancestors 'none'; form-action 'none'` など妥当。`style-src 'unsafe-inline'` は React のインラインstyleのため（許容）。`dist/_headers` は `public/_headers` と同一。**注意**：`_headers` はCloudflare配信時にのみ効く（`vite dev`・`vite preview` では効かない）。印刷用の隠し `iframe`（`blob:` のPDF）が、`object-src 'none'`＋ブラウザーのPDFビューアーで開けるかは、本レビューでは実機確認していない（未確認）。コードは失敗時にリンク表示へ落ちる（`output.ts:49-`）。
- 下書き：既定OFF（`DraftPanel.tsx:13-17,33`）、IndexedDB、30日期限、「すべて削除」、JSON書き出し／読み込み。一括の宛先一覧は保存されない（`DraftPayload` が `receipt`／`design`／`issuer` のみ）。インポート検証は型・列挙・長さ・件数・サイズ（40MB）・画像データURLの形式（PNG/JPEGのbase64のみ）を検査し、1件でも不正なら全体を拒否。`JSON.parse` の結果は新しいオブジェクトに組み替えており、`Object.assign`／深いマージがないためプロトタイプ汚染の経路は見当たらない。【事実：コード読解】

**4. 入力の安全性**
- SVGプレビュー：`dangerouslySetInnerHTML`（`Preview.tsx:34`、`SealEditor.tsx:139`）に入る文字列は、①全テキスト・属性値を `escapeXml`、②色は `paint()` で `#hex` のみ許可、③フォント名は固定、④`d` は字形アウトライン由来、⑤さらに `sanitizeSvg` で `script`／`foreignObject`／`on*`／外部 `href` を除去、⑥CSP `script-src 'self'`、の多重防御。【事実】`dataUrl` は `escapeXml` を通り、`href` は `data:image/` と `#` のみ許可。
- 画像：SVG・HEICを拒否、MIME偽装でも `createImageBitmap`→canvas→PNG再エンコードのため、出力は常にPNG（EXIFも消える）。5MB上限はデコード前に判定。【事実】デコード後の画素数の上限はない（巨大画素の画像で自分のブラウザーが重くなる可能性。自己DoSで低）【推測】。
- CSV：UTF-8（BOM有無）・Shift_JIS・UTF-16LE。Papa Parse は `header:false`・`dynamicTyping` なし（数値化されない）・`skipEmptyLines:false`。5MBはファイルサイズを読む前に判定（`BulkDialog.tsx:119`）、貼り付けは `limitSize` で切り詰め。300行で打ち切るが、パース自体は5MB全体に対して行われる（メモリ・CPUは5MBで頭打ち）。制御文字は `cleanCell` で除去（タブ・改行を除く）。取り込んだ宛名がPDFの文字として出るだけで、数式として実行される経路はない。書き出し側の無害化は L4。
- ファイル名：`領収書_YYYYMMDD.pdf`／`_N件`。日付形式が正規表現に合わなければ `nodate`。利用者入力は入らない。

**5. PDF・印刷**
- 寸法：A4=210×297、A5横=210×148、2up/控え付き=各210×148.5（`impose.ts:7-25`）。重要要素は端から9mm（枠）・角印は8mm以上に丸められ、全デザイン×全形式で検証するテストあり（`buildSheet.test.ts:236`）。裁断ガイドは端から5mm（仕様の5〜8mm内）。奇数件の下半分は空欄（`impose.ts:58`）。
- 控え：同一番号・同一金額（同じ `rc`・`tax` から生成）。印紙欄は `role='original'` のみ（`buildSheet.ts` の `stampBox`）。`PrintScaling=None` は設定済み（L9）。オーバーフローは `OutputBar`・`BulkDialog` の両方でPDF生成を停止。フォント未収録文字は警告のみ（M8・M9）。

**6. UI/UX（コード・スタイルからの読み取り）**
- 良い：モード選択が質問形式（`ModeSelector.tsx`）、既定は一般、「はい」でも既定は適格請求書（厳しい側）。エラーは「エラー／注意／お知らせ」のラベル付き（色だけに頼らない）。入力欄は44px以上、ラベル・`aria-describedby`・`aria-invalid`・`aria-live` あり、`:focus-visible` あり。スマホは入力／プレビューのタブ切替。
- 気になる点：M6・M9・M10。出力バーがスマホで画面下に固定され、プレビューを見ずにPDFを保存できる（見る・見ないは利用者次第で、プレビュー確認を促す文言は無い）。`IssueList` が欄ごとに `aria-live` を持つため、入力中の読み上げが多くなり得る。L3。
- 免責・出典：画面は `Footer`（免責・国税庁リンク・フォントライセンス）と印紙税パネル（出典と確認日）。PDF側は H2。

## 4. 良い点（3つ）

1. **一般モードの登録番号の遮断が多重**で、`effectiveReceipt`・`buildSheet`・UIの欄の非表示、それぞれに回帰テストがある。モード切替・下書き復元・一括のいずれでも構造化欄から値が出ない。
2. **税務計算が整数演算で、根拠付きの検証値をテストに固定**している。印紙税の税額表は国税庁の本文と一致し、施行日・出典・確認日がデータとして付く。判断できないケース（クレジット・QR・営業か不明など）は金額を出さず `unknown` に落とす。
3. **外部通信ゼロの設計が一貫**している（外部フォント・CDN・解析なし、CSPで `connect-src 'self'`）。SVGの出力・画像・下書きJSON・CSVの入力は、エスケープ＋サニタイズ＋型検証＋再エンコードで多重に防御されている。

## 5. 人間（発注者・税理士・弁護士）が判断すべき事項

1. **PDFへの免責・保存案内の載せ方**（H2）：受取人に渡る領収書面に載せるのは不自然なので、「控え面の下部」「PDF末尾の注意ページ」「画面の常設表示のみ」のどれにするか。完成判定5をどう満たすかの方針。
2. **税理士へ**：①適格簡易請求書で課税明細がない場合の扱い（M2）、②適格請求書の宛名として不可とする語の範囲（「お客様」等。worker-B §14 Q1）、③電子交付で「課税されない可能性」と出してよいか（根拠は注文請書の質疑応答。同 Q22）、④営業に関しない受取の既定値（現在は「営業に関する受取＝はい」が既定）、⑤一般モードの参考表示と「適格請求書ではありません」の文言（同 Q11・13）、⑥印紙税の目安表示が税務相談に当たらない範囲（同 Q28）。
3. **弁護士・運営者へ**：利用規約・プライバシーに関する文面（delta §5・Q8。現状は免責のみ）。運営名義・問い合わせ窓口（Q9）。下書き保存（IndexedDB）の取り扱いの説明。
4. **ゲストの訂正書面を Phase 1 に含めるか**（delta §3-10「ゲストの訂正は元の日付・番号を手入力」。現状は未実装）。含めないなら delta の記述を Phase 2 側へ移す。
5. 一般モードの自由記述欄に T＋13桁が書かれた場合を、警告にするかエラーにするか（M1）。
6. 登録番号のチェックデジット警告を、個人事業者に出し続けるか（M11）。
